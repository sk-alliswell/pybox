    시뮬레이션이 끝나면 여기에 보고서가 나옵니다. "시작하기"에서 고르고 실행해 보세요.

    "시작하기"에서 고른 내용이 여기 값으로 들어와 있습니다. 더 세밀하게 고치고 싶을 때만 쓰면 됩니다. 실행하기 전에 무엇을 시뮬레이션할지 정합니다. 호출자 몇 개가 어떤 모델을 얼마나 부르는지, 서버와 GPU가 몇 장인지, 게이트웨이가 요청을 어떻게 나누고 줄 세우는지입니다. 모델과 GPU의 속도는 가정값이며 직접 고칠 수 있습니다.

    요청 유형 (한 사람이 보내는 요청의 종류)

    시간 초과 후 다시 보내기 번. 기다리는 한도를 넘긴 요청을 호출자가 같은 한도로 다시 보냅니다. OpenAI와 Anthropic의 SDK는 기본 2번입니다(공개 문서). 사람이 실제로 그만큼 기다리는지는 가정입니다. 켜면 게이트웨이가 거절한 요청도 안내받은 시간 뒤에 같은 횟수만큼 다시 옵니다. "게이트웨이가 줄이는 입력"은 실제 게이트웨이의 오래된 도구 결과 정리 기능입니다. 도구를 많이 쓰는 40턴짜리 작업에서 로컬 서버로 잰 값은 35%, 계산으로는 63%였습니다(gateway/LEAD.md). 어떤 요청이 그런 작업인지는 가정입니다.

    팀 (사용 실태를 나눠 보는 단위)

    팀은 결과를 나눠 보기 위한 구분입니다. 팀원 한 사람이 모든 유형의 요청을 보내며, 유형별 빈도만 팀마다 다릅니다. 그림에서는 타일 하나가 한 사람이고, 결과 표와 그래프는 팀별로, 그 안에서 유형별로 나옵니다.

    모델 서버와 GPU

    모델을 고르면 그 모델이 해당 GPU에서 차지하는 장수, 요청 하나가 혼자일 때의 초당 토큰, 적정 동시 처리 수(요청 하나가 초당 30토큰은 받는 가장 큰 수)가 채워집니다. 측정이 그 전에 끝난 모델은 공개 측정 335건의 중앙 기울기로 곡선을 이어서 구하되 측정 끝의 4배를 넘기지 않고, 표에 측정이 몇 건까지였는지 적습니다. 함께 처리하는 요청이 늘 때 한 요청의 속도가 어떻게 줄어드는지는 모델별 측정 곡선을 그대로 따릅니다. 값은 직접 고칠 수 있고, 어디서 온 값인지는 아래 표에 있습니다.

    모델 목록과 수치의 출처

    2026년 11월 Hugging Face 다운로드가 많은 오픈 모델의 최신 버전입니다. 공개 측정은 InferenceX(SemiAnalysis)가 실제 GPU에서 동시 요청 수를 바꿔 가며 잰 원자료이고, 코딩 에이전트 부하는 같은 곳의 에이전트 트레이스 재생(n은 사용자 수)입니다. 글 1건은 한 곳의 측정 기록입니다. 환산은 같은 모델을 다른 GPU에서 잰 값을 추정식의 비율로 옮긴 것입니다. 추정은 측정이 없는 모델로, 한 토큰 시간 = 층수 × 0.08ms(희소 모델은 0.10ms) + 한 토큰이 읽는 가중치 ÷ GPU 메모리 대역폭으로 계산했습니다. 이 식은 공개 측정 22건과 비교했을 때 밀집 모델에서 중앙값 6%(최대 11%), 희소 모델에서 중앙값 15%(최대 61%) 어긋났습니다. GPU 메모리는 vLLM 프로젝트 레시피의 최소값이고, 레시피가 없으면 가중치 크기의 1.19배(레시피 21개의 중앙값 1.20)입니다. 맨 오른쪽은 이 프로젝트에서 4비트 파일을 CPU 4코어로 직접 잰 값입니다. 자세한 표와 재현 방법은 gateway/sim/reference/models에 있습니다.

    구성요소모델근거
    게이트웨이 스케줄러실제 코드(gateway/src/scheduler.rs)를 그대로 옮김: 에이전트별 FIFO, 가중 라운드로빈, 엄격 우선순위, 큐 상한과 축출, 예상 대기 시간에 따른 거절코드 이식. 실험 4개(미사용 검증)에서 큐 길이와 거절 수가 측정과 일치
    모델 서버 (로컬)슬롯 수만큼 동시 생성, 나머지는 도착 순 대기. 응답 시간 = 프리필 + 토큰 수 / 초당 토큰측정 로그에서 자동 추정(gwsim calibrate): 초당 토큰, 프리필, 요청 간 편차
    떠난 호출자의 요청서버는 프리필과 첫 토큰까지 처리한 뒤에야 연결이 끊긴 것을 알아챔직접 연결 실험 로그에서 추정. llama-cpp-python이 청크를 쓸 때마다 연결을 확인하는 동작과 일치
    LiteLLM (프록시)단일 스레드 워커가 요청당, 청크당 CPU를 순서대로 처리요청당 18 ms와 청크당 0.6 ms는 하루치 실험의 총 CPU 시간에서 역산. 부하 시 14배 증가는 아직 재현 검증 전
    호스티드 API첫 토큰 시간과 토큰 속도의 로그정규 분포, RPM/TPM 한도 초과 시 429가정. 분포 값은 시나리오에 적은 대로이며 측정 재현으로 검증하지 않음
    호스트 CPU 경합실행하려는 스레드가 코어보다 많으면 비례해서 느려짐가정. 측정 재현 시나리오에서는 끔(추정된 속도에 이미 포함)
    MCP 도구 서버동시 처리 한도와 지연 분포를 가진 대기열가정. 측정 데이터 없음
    로그 저장소 (TDB)요청 경로 밖에서 묶어서 기록. 느리면 버퍼가 쌓임초당 96,000행은 TDB 벤치마크 측정값. 게이트웨이와 연결한 상태에서는 미검증
    네트워크홉마다 고정 지연과 균등 지터가정(기본 0.2 ms, 같은 머신 기준). 손실과 대역폭은 모델에 없음

    아직 모델에 없는 것

    PR #5의 fair 정책과 적응형 동시성, 게이트웨이 응답 캐시와 프롬프트 캐시, 백엔드 장애와 중간 끊김, 게이트웨이 메모리 급증(재시도 폭주 시 390 MB까지 오른 현상). 이 항목들이 결과를 좌우하는 실험은 아직 직접 돌려야 합니다.
