# LLM 게이트웨이 사용 패턴 보고서

출처: 실제 게이트웨이 로그 (TDB), 모델 서버 3대가 10시 무렵 모두 죽은 실행. 요청 880건, 관측 구간은 하루의 1.0배입니다. 하루를 1,800초로 줄여 넣은 부하이고, 시간대는 그 하루를 24로 나눈 것입니다.

## 요약

- **11~24시에는 요청이 밀리는데 서버는 슬롯의 30%도 쓰지 않았습니다.** 부하가 아니라 장애 모양입니다. 모델 서버가 죽었거나, 게이트웨이가 살아 있는 서버로 요청을 보내지 못한 시간대인지 먼저 확인해야 합니다.
- 팀들이 같은 시간대에 몰립니다. 전체가 가장 바쁜 세 시간의 요청량이 각 팀의 가장 바쁜 세 시간을 더한 값의 99%입니다(100%면 완전히 겹침). 대기가 길어지는 시간대는 9~24시이고, 한가한 시간대는 0~8시, 11~24시입니다. 팀별 주 사용 시간을 어긋나게 하면 같은 서버로 이 시간대의 대기를 줄일 수 있습니다.
- 서버가 하루에 슬롯 기준 59시간만큼 비어 있습니다(0~8시, 11~24시 사용률 30% 미만). 급하지 않은 batch 요청이 서버 시간의 22%를 쓰고 있으니, 이 요청을 한가한 시간대로 미루는 것이 첫 후보입니다.
- 호출자 상위 10%가 서버 시간의 43%를 씁니다. 가장 많이 쓰는 호출자는 product-1(16%)입니다. 과부하 때 이들이 나머지의 대기를 늘리므로, 적게 쓴 사람 먼저 내보내는 줄 세우기나 호출자별 한도가 효과를 볼 조건입니다.
- 입력 토큰 중 캐시로 다시 읽지 않은 비율은 전체 31%입니다. 25%에 못 미치는 묶음: product batch (19%), research batch (23%). 공개 트레이스에서는 첫 요청도 프롬프트의 42~57%가 다른 요청과 겹쳤으므로, 이보다 낮으면 분배가 캐시를 흩고 있거나 서버가 기억하는 앞부분 수가 모자란 것입니다.
- 응답을 받지 못한 요청이 78%입니다(거절 16%, 호출자 포기 62%). 가장 심한 묶음은 research interactive로 46건 중 37건입니다.
