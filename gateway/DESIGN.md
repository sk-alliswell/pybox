# pybox-gateway 설계

## 1. 왜 필요한가

에이전트 10~20개가 각자 LLM API를 직접 호출하면 다음 문제가 동시에 생긴다.

| 문제 | 직접 호출 시 | 게이트웨이 적용 후 |
|---|---|---|
| 연결 | 에이전트마다 TCP/TLS 핸드셰이크, 커넥션 따로 유지 | 업스트림마다 풀 하나. keep-alive, HTTP/2 다중화 |
| 429 | 같은 키 한도를 20개가 나눠 쓰다 동시에 429를 맞고, 동시에 재시도해서 더 악화 | 토큰 버킷으로 사전 페이싱. 429를 맞으면 업스트림 전체에 공유 쿨다운 |
| 공정성 | 루프를 도는 에이전트 하나가 한도를 독점 | 에이전트별 큐 + 가중 라운드로빈, 에이전트별 동시 실행 상한 |
| 스트리밍 | 클라이언트가 죽어도 업스트림 생성은 계속되어 토큰 낭비 | 클라이언트가 끊기면 즉시 업스트림 요청 취소 |
| 키 | 게스트마다 실제 API 키 주입 | 키는 호스트에만. 게스트는 폐기 가능한 에이전트 토큰만 보유 |
| 관측 | 사용량이 흩어짐 | 에이전트별 요청, 토큰(캐시 포함), 대기시간, TTFB, 에러 집계 |

pybox는 게스트 네트워크가 꺼져 있다(`docs/ARCHITECTURE.md`). 그래서 LLM 호출은 어차피 호스트가 중개해야 하고, 이 게이트웨이가 그 중개자다.

## 2. 위치

```
 pybox 게스트 (에이전트 런타임)          호스트
 ┌──────────────┐  에이전트 토큰   ┌──────────────────────────┐   실제 키    ┌───────────┐
 │ agent SDK    │ ───────────────▶ │ pybox-gateway (loopback) │ ───────────▶ │ LLM API   │
 │ base_url=GW  │ ◀── SSE 그대로 ── │ 큐·페이싱·재시도·집계      │ ◀── SSE ──── │           │
 └──────────────┘                  └──────────────────────────┘              └───────────┘
        ▲                                     ▲
        └──── pybox manager: 샌드박스 시작 시 POST /gateway/agents 로 토큰 발급, 종료 시 DELETE
```

- 경로 규칙: `http://127.0.0.1:8787/<upstream>/<원래 경로>`. SDK의 `base_url`만 바꾸면 되고 요청 형식은 그대로다.
- 요청 바디를 다시 직렬화하지 않고 바이트 그대로 전달한다. 그래서 프롬프트 캐시(`cache_control`, OpenAI 자동 캐시)의 프리픽스가 깨지지 않는다.
- 별도 크레이트(`gateway/`, 자체 workspace)라서 pybox 컨트롤러의 의존성, Cargo.lock, "CLI 네트워크 비활성" 정책은 바뀌지 않는다.

## 3. 요청 흐름

1. **인증**: `x-api-key` 또는 `Authorization: Bearer`의 에이전트 토큰으로 에이전트를 찾는다. 모르는 토큰은 업스트림에 닿기 전에 401로 끝난다.
2. **예산 확인**: `token_budget`을 다 쓴 에이전트는 429 `gateway_budget_exceeded`를 받는다.
3. **캐시(선택)**: 스트리밍이 아니고 `x-gateway-cache: on`인 요청은 `(업스트림, 경로, 바디)`의 SHA-256 키로 조회한다. 동일 요청이 진행 중이면 기다렸다가 결과를 공유한다(coalescing).
4. **큐잉**: 업스트림 스케줄러의 에이전트별 FIFO에 들어간다.
5. **디스패치**: 업스트림마다 하나뿐인 디스패처가 다음 조건을 모두 만족할 때 `Lease`를 발급한다.
   - 전체 동시 실행 < `max_concurrency` (세마포어)
   - 해당 에이전트 동시 실행 < 에이전트 `max_concurrency`
   - RPM 버킷, 입력 TPM 버킷(바디 바이트/4로 추정)에 여유가 있음
   - 공유 쿨다운이 끝남
6. **전송**: 업스트림별 풀 클라이언트로 보낸다. 실제 키를 주입하고, `accept-encoding`은 제거한다(사용량 파싱을 위해 비압축으로 받음. 루프백이라 손해 없음).
7. **재시도**: 408/429/500/502/503/504/529와 연결 오류는 재시도한다(`x-should-retry`가 있으면 그 값을 따름). 응답 바이트가 클라이언트로 나가기 전에만 재시도하므로 클라이언트 입장에서는 보이지 않는다.
   - 429/529: `retry-after-ms`/`retry-after`(없으면 지수 백오프+지터)만큼 **업스트림 전체 쿨다운**을 걸고, 다시 큐에 들어간다. 다른 에이전트도 같이 쉬기 때문에 429 폭풍이 생기지 않는다.
   - 5xx/연결 오류: 해당 요청만 백오프 후 다시 큐잉한다. 기다리는 동안 슬롯은 반납한다.
   - 재시도를 다 쓰면 마지막 업스트림 응답을 그대로 돌려준다. SDK 자체 재시도 로직도 정상 동작한다.
8. **스트리밍 응답**: 바디를 그대로 흘려보내면서 옆에서 SSE `data:` 줄만 파싱해 usage를 모은다. `Lease`는 바디 스트림 안에 들어 있어서 스트림이 끝날 때까지 슬롯을 차지하고, 클라이언트가 끊으면 바디가 drop되면서 업스트림 연결이 닫히고 슬롯이 즉시 반납된다. 백프레셔는 hyper가 처리한다(클라이언트가 느리면 업스트림 읽기도 느려짐).
9. **정산**: 실제 입력 토큰으로 TPM 추정치를 보정하고, 에이전트별 토큰(입력/출력/캐시 읽기/캐시 쓰기)을 누적한다.

## 4. 스케줄러

- 업스트림마다 `Scheduler` 하나와 디스패처 태스크 하나를 둔다. 디스패처가 하나라서 레이트리밋 대기는 업스트림 전체에서 한 번만 일어난다.
- `ring`: 대기 요청이 있는 에이전트들의 라운드로빈 순서. 맨 앞 에이전트는 한 바퀴에 `weight`번 연속으로 받는다.
- 맨 앞 에이전트가 자기 상한에 걸려 있으면 건너뛰고 다음 에이전트에게 준다. 한 에이전트가 막혀도 나머지는 계속 진행된다.
- 대기 중에 클라이언트가 포기한 요청(oneshot 수신자 drop)은 건너뛰고, 슬롯을 소비하지 않는다.
- 레이트리밋 대기 중에는 세마포어 퍼밋을 쥔 채 잔다. 업스트림 슬롯이 어차피 쓰일 수 없는 시간이라 손해가 없다.

## 5. 캐시와 coalescing

LLM 응답은 temperature가 0이어도 완전히 결정적이지 않다. 그래서 기본값은 꺼짐이고, 요청 헤더 `x-gateway-cache: on`(또는 `cache.default_on`)일 때만 동작한다. 2xx 응답만 저장하고, 리더 요청이 실패하면 대기하던 요청들은 각자 업스트림으로 간다. 대표 용도는 같은 시스템 프롬프트로 여러 에이전트가 동시에 시작할 때의 중복 분류/라우팅 호출이다.

## 6. 보안 경계

- 기본 바인드는 `127.0.0.1`. 루프백이 아니면 경고를 남긴다.
- 실제 키는 설정 또는 환경변수(`api_key_env`)에서만 읽고 응답이나 통계에 나오지 않는다.
- 에이전트 토큰은 `POST /gateway/agents` 응답에서만 한 번 보이고, `DELETE`로 즉시 폐기된다.
- 관리 API는 `admin_token`으로 보호한다(상수 시간 비교).
- 이 게이트웨이는 멀티테넌트 서비스 인증 계층이 아니다. pybox와 같은 단일 사용자 호스트용이다.

## 7. pybox 연동 (다음 단계)

현재 pybox 게스트는 네트워크가 없으므로 게스트에서 게이트웨이까지 가는 다리가 필요하다. 두 가지 선택지가 있다.

1. **호스트 함수 브리지(권장)**: Hyperlight 호스트 함수로 `llm_request(upstream, path, headers, body)`와 스트리밍 청크 콜백을 노출하고, 호스트 쪽에서 게이트웨이(루프백)로 전달한다. 게스트에는 범용 네트워크가 열리지 않고, LLM 호출만 허용된다.
2. **게스트 내 HTTP 셔틀**: 게스트 안에 작은 HTTP 서버 흉내를 두고 SDK `base_url`을 그쪽으로 향하게 한 뒤 위 브리지를 탄다. SDK 수정 없이 붙일 수 있다.

매니저는 샌드박스 시작 시 에이전트 토큰을 발급해 게스트 환경에 넣고, 종료/정리 영수증 단계에서 토큰을 폐기한다. 이 부분은 pybox의 lifecycle 변경이라서 `verify.py`로 WHP/KVM 검증이 필요하고, 이번 범위에서는 하지 않았다.

## 8. 한도 (토큰, 금액, 요청 수, 도구 호출)

기준선은 LiteLLM의 key/user/team budget과 Envoy AI Gateway의 토큰 기반 rate limit이다. 둘 다 "누가, 어떤 기간에, 무엇을 얼마나"의 조합이라서 규칙 하나를 그 세 축으로 표현했다.

- **범위**: `global`, `agent`, `key`, `user`, `team`, `project`, `session`. `match`(glob)로 대상을 좁히고 `model`, `upstream`, `tool`로 한 번 더 좁힌다. 규칙은 대상 값마다 따로 센다.
- **기간**: 롤링(`30s`, `1m`, `1h`, `7d` 등. 버킷 두 개로 근사하는 슬라이딩 윈도)과 달력(`day`, `month`, UTC).
- **상한**: `requests`, `tokens`, `usd`, `tool_calls`. 한 규칙에 여러 개를 함께 둘 수 있다.

요청이 들어오면 먼저 예약하고 끝나면 실제 사용량으로 정산한다. 예약이 없으면 동시에 들어온 요청들이 모두 "아직 남았다"고 보고 통과해서 한도를 크게 넘기 때문이다. 기본은 입력 추정치만 예약하고, `strict = true`면 `max_tokens`까지 예약해서 한도를 절대 넘지 않게 한다(대신 동시 실행이 줄어든다). 응답이 오지 않고 끊기면 예약은 그대로 반납된다. 거절은 429와 `retry-after`로 돌려주고 어느 규칙에 걸렸는지 본문에 적는다.

금액은 업스트림이 비용을 알려주면(LiteLLM의 `x-litellm-response-cost`) 그 값을 쓰고, 없으면 가격표로 계산한다. 재시작하면 요청 로그에서 현재 기간의 사용량을 다시 읽어 복원한다. 규칙은 설정 파일과 `PUT /gateway/limits/{name}`으로 넣고, 런타임 규칙은 백엔드 메타에 남는다.

## 9. 도구(MCP) 트래픽 제어

기준선은 agentgateway와 Docker MCP Gateway다. `/mcp/{server}`가 MCP Streamable HTTP를 그대로 프록시하고, 에이전트는 LLM 호출과 같은 토큰으로 인증한다.

- 서버 단위 `allow_tools`/`deny_tools`와 에이전트 단위 `mcp_allow`/`mcp_deny`(`server/tool` glob). 막힌 도구는 `tools/list` 응답에서도 지워서 모델이 고르지 않게 한다.
- `tool_calls` 한도는 §8의 규칙을 그대로 쓴다. 한도에 걸리면 JSON-RPC 오류가 아니라 `isError` 결과로 돌려줘서 에이전트 루프가 죽지 않고 모델이 상황을 읽을 수 있다.
- 서버별 동시 실행 상한과 분당 호출 수는 LLM과 같은 공정 스케줄러를 쓴다.
- `max_result_bytes`로 도구 결과 크기를 자른다. 큰 결과는 그대로 다음 요청의 입력 토큰이 되기 때문이다.
- 호출마다 `tools` 테이블에 행을 남기고 스팬(`tools/call {tool}`)과 지표를 낸다. 요청의 `params._meta.traceparent`가 있으면 그 트레이스에 붙는다.

## 10. OpenTelemetry GenAI 규격

규격은 `open-telemetry/semantic-conventions-genai` 저장소 기준(2026-11 현재 Development 단계)이다. 내부 표현을 규격 이름으로 바꾼 것이지 별도 계층을 얹은 것이 아니다.

- 루트 스팬은 `chat {model}`, kind CLIENT. 속성은 `gen_ai.operation.name`, `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.response.model`/`id`/`finish_reasons`, `gen_ai.usage.input_tokens`/`output_tokens`/`cache_read.input_tokens`/`cache_write.input_tokens`, `gen_ai.conversation.id`, `server.address`/`port`, `error.type`. 게이트웨이 고유 값은 `pybox.*` 아래에 둔다.
- 지표는 `GET /gateway/metrics`(Prometheus 텍스트)로 낸다: `gen_ai.client.inference.duration`, `time_to_first_chunk`, 토큰 사용량, `mcp.client.operation.duration`, 거절 수. 시리즈 수는 512개로 막는다.
- `otlp_export`를 설정하면 스팬을 OTLP/HTTP(protobuf)로 묶어서 내보낸다. 큐가 차면 버리고 요청 경로는 기다리지 않는다. 트레이스 하나는 `GET /gateway/traces/{id}?format=otlp`로도 받을 수 있다.
- 받는 쪽에서는 예전 이름(`gen_ai.system`, `prompt_tokens`, `llm.usage.*` 등)을 규격 이름으로 바꿔서 저장한다.

## 11. 단일 서버 효율

여러 서버로 나누지 않으므로 한 프로세스가 요청당 쓰는 CPU와 덧붙는 지연을 줄이는 쪽을 택했다. 기준선은 TensorZero, Bifrost, Helicone이 내세우는 1ms 미만의 추가 지연이다. 수치와 방법은 [BENCH.md](BENCH.md)에 있다.

- 받은 소켓에 TCP_NODELAY가 빠져 있어서 짧은 응답과 첫 토큰이 약 40ms씩 늦던 문제를 고쳤다.
- SSE 사용량 파서는 usage나 finish_reason이 있을 수 있는 줄만 JSON으로 푼다. OpenAI는 모든 청크에 `"usage":null`을 싣기 때문에 null은 건너뛴다.
- 요청 본문은 다시 직렬화하지 않고 필요한 필드만 끼워 넣는다.
- 과부하일 때는 쌓아두지 않고 빨리 거절한다. 업스트림별 `max_queue`를 넘거나 `queue_timeout_secs` 동안 순서가 오지 않으면 503과 `retry-after`를 준다.
- 업스트림 HTTP/2 연결에 keepalive를 걸어 죽은 연결을 일찍 버린다.

## 12. 의도적으로 뺀 것 / 향후

- 여러 서버로의 분산(공유 한도 카운터, 공유 캐시). 한도 상태가 프로세스 메모리에 있으므로 게이트웨이를 여러 대 띄우면 한도가 대수만큼 늘어난다.
- MCP 서버 여러 개를 하나의 엔드포인트로 합치기(federation), stdio 서버 실행, OAuth 중계.
- 청크 사이 간격 지표(`time_per_output_chunk`). 프록시 위치에서는 네트워크 묶임 때문에 모델의 실제 간격을 잴 수 없다.
- 토큰 modality 구분(항상 `unknown`), OTLP/JSON 수신, 대시보드의 도구 호출 탭.
- 응답 헤더 기반 적응형 페이싱(`anthropic-ratelimit-*-remaining`, `x-ratelimit-remaining-*`).
- 업스트림당 여러 키와 에이전트 고정(sticky) 라우팅.
- 출력 토큰 예산을 스트림 도중에 끊는 hard limit(현재는 `strict` 예약으로 사전에 막는다).
- 메모리 백엔드는 행을 통째로 들고 있어서 4만 건에 약 720MB를 쓴다. 장기 운영은 TDB 백엔드를 쓴다.

## 13. 검증
